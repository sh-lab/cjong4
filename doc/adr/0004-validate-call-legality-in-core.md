# ADR 0004: 鳴き後の打牌可能性をcoreで検証する

## ステータス

採用

## コンテキスト

チー／ポンの判定が面子の成立条件だけを確認すると、喰い替え禁止によって残った手牌を1枚も捨てられない鳴きを許可してしまいます。managerで候補を除外しても、coreを直接使う利用側には同じ問題が残ります。

打牌にはルールを省略するAPIとルール対応APIが併存しており、利用側の選択によって禁止を暗黙に迂回できていました。

## 決定

v4ではチー／ポンの判定・実行APIにルール引数を追加し、coreが鳴き後の打牌可能性まで判定します。使用牌を指定しない判定も、使用牌を指定する完全な判定から導出します。

判定は内部の共通遷移で状態のコピーを作り、既存のルール対応打牌判定で合法な打牌の存在を確認します。実行APIも同じ判定を呼び、不正な鳴きはビルド設定にかかわらず入力状態のまま返します。内部の未検証遷移は公開ヘッダーに含めません。

managerはcoreの判定を利用し、独自の鳴き後チェックを持ちません。鳴き・打牌の判定と実行では同じルールを使用します。

打牌の判定と実行には、第2引数にルールを受け取る `cj4_can_discard()`／`cj4_do_discard()` を使用します。`NULL` を明示したときの既存の喰い替え許可動作は維持し、通常は対局のルールを渡すことを公開ヘッダーと移行文書に記載します。

## 結果

- manager経由とcore直接呼び出しで合法性の判定を共有できます。
- 喰い替えの判定式を複製せず、打牌判定の変更を鳴きにも反映できます。
- 判定は入力状態を変更せず、鳴き実行と同じ状態遷移を使います。
- v3の利用側は引数追加と旧打牌APIからの移行が必要です。互換ラッパーは設けません。
- 他の状態遷移APIの不正入力時の契約は、この変更では変更しません。
